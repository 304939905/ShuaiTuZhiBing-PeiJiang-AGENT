# 逐帧判读作业书（1 秒/帧深度学习）

## 背景

《率土之滨》（网易 SLG 手游）抖音攻略视频深度学习项目。作者是 UP 主「北冥」。
每个视频已按 **1 秒/帧** 全量抽帧，你的任务是**逐帧判读画面**，产出一份结构化 JSON，
主控会用它渲染成 Word 报告。

这些视频有大量信息**只存在于画面**：队伍界面、武将卡、战法图标、战报结果、
硬字幕大字、UI 数值。音频转写（whisper）经常把武将名/战法名转错。
**逐帧判读的价值就在于补齐和校正这些画面信息。**

## 项目定位（重要，先看这段）

- 本项目服务的是**平民玩家**——**低充值玩家**：武将卡少、可学战法少、战法等级不高、宝物与红度不足。报告的全部价值在于帮这类玩家**按自己账号的资源条件**做配将 / 配战法决策，而不是复述土豪满红打法。
- 所以你判读时，看到阵容 / 战法 / 宝物，**要额外留意"平民能不能凑、缺了用什么下位替代、红度 / 等级门槛"**，把这些写进 report。
- 各批次的 frames 目录与 json 目录以主控实际派发为准（海之呼唤 / 赛季 / 阵容 各有独立目录，路径见下方素材清单）。

## 可忽略的无关信息（重要）

本项目服务平民玩家做配将/配战法，**以下信息与主要目的无关，判读时无需当作实体重点，可直接略过或最多一笔带过，不要花篇幅、不要当作待核实项**：
- **玩家名 / 昵称**：如粉丝投稿里的「云剑」「海棠巾」「清河」「老舅」「天天涨停」「小诗」等。
- **同盟名**：如「苍穹等盟」「邪恶集团」等。
- **队伍绰号 / 粉丝队名（非体系名）**：如某投稿者自命名的小队，对"该抄哪队"无帮助。
- **地理/要塞/坐标 UI 文本**：如「宛要塞」「西华要塞」「司隶」「Lv.7 土地」等纯地图信息（除非它直接说明某队的驻防/克制关系）。
- 反之，**体系名（神赏/螃蟹队/斩龙/碰瓷/网红队等）要保留**——它们直接描述配将思路，是核心知识。

> 白名单闸门已把这些"真实但无关"的词（玩家名/同盟名/队名/地理UI）纳入 `gate_extra_known.json`，不会被误判为编造；但本规则要求的是**在判读阶段就别写它们进报告**，而不是等闸门放行。

## 质量红线

1. **不编造，且必须"看画取证"**。你（子智能体）有 Read 工具，能读图。
   **写每个实体名前先读对应静帧**，从画面转录；听音频只是为了定位时间点，不能代替看画面。
   看不清就写「无法识别（OCR存疑）」，查不到就写「查不到」，放进 `limitations`。
   宁可少写一条，也不要写一条假的、猜的。
2. **具体优先**。不要写"作者展示了一个队伍"，要写"01:41 显示队伍为郭嘉+荀彧+贾诩，
   战法含反计之策、锦囊妙计"。写不出具体的说明你没回看原图。
3. **文件名必须真实存在**。写 `file` 字段前先 `ls` 或按 `frame_%04d_MM-SS.jpg` 规则算准，
   序号从 0 开始（第 0 秒 = frame_0000_00-00.jpg，第 65 秒 = frame_0065_01-05.jpg）。
   写错会在报告里渲染成红色「图缺失」。
4. **timeline 插图总数控制在 20–40 张**，挑有信息增量的帧，不要连续放几乎相同的画面。
5. 中文引号统一用「」，不要用英文双引号或中文弯引号，避免 JSON 转义出错。
   注意：`「」` 只能出现在**字符串值内部**，JSON 本身的键名/值的定界符必须是半角 `"`。
   写成 `"desc": 「文字」"` 是错的，正确是 `"desc": "「文字」"`。
6. `video_title` 必须与源 mp4 文件名（去掉 .mp4）**逐字一致**，含空格和标点。
7. **JSON 必须写成多行缩进格式（2 空格缩进），严禁把整个 JSON 压成一行。**
   单行超长内容会在写入时被截断，导致文件残缺、结构丢失。
8. **写完必须自检**：用 Read 重新读取自己写的文件，确认
   ① 文件结尾是完整的 `}`；
   ② 顶层字段齐全，必须同时存在 `video_title / video_id / frames_dir / duration_s /
     frame_count / sheet_count / resolution / report_date / summary / timeline /
     comparison / frame_only_value / limitations / glossary / sources` 共 15 个键；
   ③ `timeline` 是数组且非空。
   若发现残缺，重新写一遍（可拆成两次 Write：先写前半再用 Edit 追加），直到自检通过。

## 工作步骤建议

1. 读 schema → 读既有报告 JSON → 读音频转写（建立预期）
2. 顺序读全部 contact sheet，记录画面明显变化的时间点（标题卡、界面切换、战报）
3. 挑 15–25 个关键时间点回看单帧原图，确认具体名称与数值
4. 遇到不懂的术语查术语库 / WebSearch
5. 对照既有报告，整理出「画面独有」「修正」两类结论
6. 写 JSON

## 最终报告去冗余要求

- 删除与核心结论无关的内容：**粉丝 ID / 头像 / 片头片尾 / 过渡动画 / 同盟名 / 地图要塞坐标 UI / 纯战报数字堆叠**等。
- 聚焦两类精华：①作者对体系/机制的讲解；②作者对具体阵容的点评与可执行建议。
- 报告里每出现一次武将 / 战法 / 宝物名，都要能追溯到单帧画面 + 交叉核验结论；不要把"可能"、"听起来像"写进正文。

完成后回复一句话：写入成功 + timeline 帧数 + 发现的修正条数。150 字以内。

## 报告格式四大硬标准（每份报告必须含）

1. **报告索引块（检索用，放在标题之后、正文之前）**
   - 含：关键词（逗号分隔，如 攻其不备、体系讲解、配将、阵容点评）、核心武将（带版本标签，见下条）、报告生成日期、报告路径。
   - **关键词从「核心结论」提取（2026-08-21 用户规则，防冗余）**：只写体系黑话（撸铁/网红/魏智/核弹/螃蟹/神赏 等）+ 核心武将名，**限 12 个内**；**严禁全并 glossary 术语表**（glossary 可能上百词，作关键词=纯冗余）。渲染器已内置 extract_keywords()，子智能体在 `ai_inference`/`entities.teams.name` 写清核心结论即可。
   - **glossary 字段只收真「黑话/术语」**（玩家行话、体系名、机制名，如 撸铁/降配/双减/神赏），**不收画面字段**（红度/Lv.40/cost/上阵ID/S2标识/星级等）——画面字段在 timeline desc 里自然出现，重复列举无信息增量；**疑问标注（如「垒实迎击(疑似枭姬+反击)」）严禁进 glossary**，确认不了的进 limitations。
   - 同时把该条目追加进 `资料库/reports_index.md`（主索引），便于日后一键生成索引目录。
2. **武将版本标签（固定格式 + 固定出现位置）**
   - **格式**：`阵营-兵种-星级（SP 版末位加 (SP)）`，例：`蜀-步-5星(SP)`、`群-骑-5星`、`群-步-5星`。
     **名字绝不嵌入标签**（错误示范：`群-木鹿大王-骑-5星`、`群-兀突骨-步-5星` —— 名字已在标签外写出，标签内只填 阵营-兵种-星级）。
   - **判定以「自带战法」为主键**：用武将在画面上的自带战法反查本地库（hero.json / hero_extra.json 的 methodName）确定 阵营/兵种/星级/SP，禁止凭记忆手写；本地库冲突或覆盖不到的，必须 WebSearch 核验（优先网易大神 ds.163.com）。
   - **⚠️ 星级必须用「固化表」+ methodId 精确匹配（2026-08-21 铁律，星级曾三次大面积出错）**：星级权威源 = `资料库/hero_star_fixed.json`（固化表，298 武将）→ 底层逻辑 = `hero_extra.methodId → hero.json.skill_init → quality`（自带战法 ID 精确匹配版本）。**严禁** ①用 hero_extra.quality（`4-SR` 是品质字段非星级，且库内无 5 星卡）②按 hero.json 同名首条/末条取（同名普通/SP/XP 多版本会取错）。画面武将卡星级（子智能体逐帧转录）**不可靠**（曾把"4 红"误读成"4 星"），须以固化表为准。渲染器已内置，子智能体只需在 entities.teams.positions 写清武将名 + skills 首项=自带战法名。
   - **出现位置（关键，避免冗余）**：版本标签**只出现在两处**——① 报告开头「核心武将（版本）」清单（平铺所有提及武将）；② 阵容表格的「武将」列（逐投稿对照参考）。**正文 prose（结论/讲解/点评/作者建议/AI 推断段）一律只写武将名，不重复版本标签，除非出现重名（如普通版与 SP 版同名的张飞/关银屏等，此时在正文用「张飞(SP)」区分）。** 开头清单 + 表格列已提供版本，正文无需再写。
   - **位置词（中军 / 前排 / 前锋 / 大营）严禁并入武将名**：武将标识只有「版本标签」一种，例如兀突骨写作 `群-步-5星`，**绝不写成「中军兀突骨」「前排董卓」「大营祝融」**。
   - **位置由阵容排序承载，且非武将固有属性**：一份阵容按「大营 / 中军 / 前锋」顺序列出武将（第一行=大营、第二=中军、第三=前锋），位置从排序即可读出。武将资料里标注的推荐站位只是**系统建议、并非强制**——某将可放在任意位置（如作者建议"把大营位的祝融替换为兀突骨"，即兀突骨接大营）。
   - **替换/替代表述固定写法**：「用 X 替换大营位置的 Y 抓法刀」（X 不带版本、不带位置；「大营位置的」只作目标槽位限定）。不要写「用中军位的 X 替换大营位的 Y」（易误解 X 固定中军）。
   - 武将版本对照表（表格「武将」列）表头写「武将（阵营-兵种-星级）」，单元格只填 武将名 + 版本标签，不写位置。
3. **报告生成日期（唯一时间戳，中性字段，不放警告语）**
   - 报告索引块内只写一行：`报告生成日期：YYYY-MM-DD`（即本份分析报告的实际完成日）。
   - **禁止在报告任何位置写「可能已过时 / 以官方更新为准 / 请结合时间戳判断是否过期」等时效性警告语。** 日期只是给阅读者（人）判断新鲜度的中性事实，不是给后续 AI 的谨慎指令；是否过期由人来判断，不要写进报告指挥模型。
4. **AI 主动推断内容必须单独成章、明确标注（重要，避免"事实"与"推断"混淆）**
   - 你（AI）对本游戏机制的**主动推断、延伸建议、下位替代思路、宝物/站位判断**，**严禁混写进视频事实部分**（核心结论 / 体系讲解 / 阵容点评 / 作者建议 等）。
   - 必须在 JSON 顶层新增 `ai_inference` 字段（数组），并在渲染报告中单独成章（标题示例：「六、AI 智能体主动推断内容（非视频原话，供参考）」），章节开头写明"以下为 AI 基于本地库+网易大神核验后的主动推断，非视频原话，不代表作者观点"。
   - `ai_inference` 每项建议写成对象：`{"point": "推断结论", "evidence": "依据（本地库字段/网易大神链接/画面时间点）", "confidence": "高/中/低"}`；也可写纯字符串。
   - **推断前强制核验（杜绝盲推）**：凡涉及"某将要带某宝物/某将可替代某将/某将站位"的推断，必须先查本地库相关字段（hero_extra.json 的 `distance` 攻击距离、`type` 兵种、`quality` 星级/COST 等）并与网易大神 ds.163.com 交叉核对，把证据写进 `evidence`。**禁止凭"通用原理"或记忆盲推**。攻其篇曾犯两类盲推错误，均因未查 `distance`/画面站位即下结论：①误推"吕布大营首选钜黍"——实际吕布攻击距离4已满足、不需钜黍补距离（仅祝融距离3需钜黍+1补足）；②误推"凑不齐曹操用兀突骨当前排"——曹操从未在视频出场，且把武将资料里的推荐站位当成固定约束（兀突骨可放大营，位置非强制）。
   - 鼓励主动推断与总结（这是学会玩游戏的核心目的），但**推断与事实必须物理隔离、且每条推断可溯源**。

## 工程化与交付注意事项（防复发）

- **用户真实桌面 = `D:\Desktop`**（项目根在 `D:\Desktop\shandou`）。**不是** `C:\Users\Administrator\Desktop`（那是另一账户目录，用户看不到）。交付文件一律放 `D:\Desktop`。
- **改报告必须改生成器母本，不能只覆盖 docx**：docx 由 `gen_*.py` 渲染。只手改 docx 而不改母本，下次重渲会复发旧错。所有文案修正都落到 `.py` 源（或 `frame_json` + 渲染器）。
- **渲染脚本须注入 PYTHONPATH**，否则 `No module named 'docx'`：
  `PYTHONPATH="D:/WorkBuddyData/python-env/shandou/Lib/site-packages" <managed-python> <script>.py`
