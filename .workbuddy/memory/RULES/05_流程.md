## 派发模式与监督（2026-08-22 22:27 用户拍板，当前有效）

- **子智能体派发模式**（主会话直接执行太耗 token，弃用）。
- **主会话必须监督子智能体**（用户硬性要求）：
  1. **读图留痕**：子智能体必须用 `vision_recon_driver.py` 批量调用视觉模型，输出落 `资料库/zhenrong_recon/<视频名>_recon.md`；关键帧再用 `vision_glm.py` 定向复核并追加留痕。**禁止只凭 Read 读图写报告**（Read 图像有缓存/幻觉）。
  2. **定期磁盘巡查**：主会话在子智能体运行期间定期 `ls -l` 留痕文件，核验 ①文件在增长（mtime 新鲜）②`## frame_` 段数递增 ③内容是真实视觉输出（非模板空话）。留痕不增长=子智能体没在调视觉模型，立即介入。
  3. **交付后抽帧对账**：JSON 交付时主会话随机抽 3–4 帧 vision_glm 定向判读与 JSON 对账。
- 监督巡查节奏：子智能体后台运行期间，用 TaskOutput 非阻塞 + 磁盘 ls 交替检查；发现停滞/留痕缺失即暂停询问或接管。

## 标准循环（前台串行派发，不要后台批量）

1. **派发子智能体**（作业书 `资料库/FRAME_AGENT_BRIEF_ZHENRONG.md`，schema `frame_report_schema.md`，样板看已完成 JSON）+ **监督**（见上节）
2. **磁盘复核**（子智能体静默失败率 ~10%，光看回复会漏）
3. **JSON 语法检查**（⚠️ 字符串内禁 ASCII 双引号——状态机转中文弯引号修复；值结束引号后中文逗号也判结束）
4. **帧落地核验**（ls 目录核对实际文件名）→ 5. **实体核验**（武将/战法/宝物/词条 vs 白名单+误读映射表）→ 6. **抽帧核验**（vision_glm 定向判读对账）→ 7. **汇报**

## 配将与账号诊断前检查（2026-09-01 补充）

**武将等级固定默认值（2026-10-12 用户确定）：配将时，武将等级默认按30级计算。**此为配将计算默认值，不代表账号武将实际等级。

在输出配将、战法分配、拆解或账号诊断结论前，先按 `资料库/官方机制库/基础机制判断规则_20260901.md` 做结构检查：

1. 用本次账号截图/当前客户端锁定武将版本、星级、觉醒、已占用资源与当前赛季。
2. 在生成阵容候选、战法提升建议和当前环境克制分析前，读取 `official_skill_db.json` 的 `season_tag`、`acquisition_stage` 与 `acquisition_stage_status`。S2/S3标签和明确晚于当前赛季的获取阶段直接排除；XP只是标签，禁止直接等同某个赛季。XP拆解类或兑换类战法若标为`provisional_default`，按征服赛季做保守过滤但必须视为暂定；只有它会显著改变方案时才请用户进一步核验。
3. 核对三阵位、COST、武将攻击距离、战法有效距离、兵种限制、发动逻辑、效果冲突、属性关联、队内协同与全局可学习数量。效果冲突必须执行 `资料库/官方机制库/战法冲突判定规则_20260901.md`：同类相同持续性/属性增减按数值替换，同类相同增益/减益/控制按后释放者失效，分兵/连击/规避等状态不可叠加。
4. 官网旧文章只提供结构框架；所有数值、发动率、目标数、距离数值、拆解材料、施政、宝物和赛季规则均回到当前客户端/当期官方资料/用户截图核实。战法冲突的上述底层规则为用户确认的稳定机制，不按旧文时效性降级；但具体战法是否属于相同效果、是否有独立副效果，仍须读取当前文本。
5. 输出中分开写“已核实”“结构判断”“待复核”，不得用视频精编报告或旧攻略覆盖当前资产与当前机制。

### 账号解析与方案验收（2026-09-16 补充）

1. 百家社原始导出属于敏感文件。先用 `工具/配将服务/parse_account.py` 做只读检查；只有用户明确要求建立账号档案时才写出脱敏 `account-profile.json`，原始导出不得收入资料库。
2. 武将和战法优先用内部 ID 关联，禁止仅凭同名锁定版本。武将星级以同ID且自带战法一致的 `hero.json.quality` 为准，不把 `hero_extra.quality` 的 `4-SR` 当成4星。解析器无法匹配的可配实体必须列为 `unresolved`，不得进入正式编队；系统侍卫等非可配记录只能列为 `ignored`，不能混入武将池。账号导出未包含的研究进度和宝物所有权不得补猜。
3. 战法数量按用户 2026-09-20 确认的 `空闲/总份数` 解释；已分配=总份数−空闲，`0` 不等于未拥有。**以后配将默认以账号可分配总份数核算新阵容，不以当前空闲份数设上限。**默认旧队可拆并收回战法；若用户明确保留旧队，只把保留项列入 `existing_occupancy` 并与新队一起核总数。原始导出仅含空闲数，总份数暂由本地 `skill_extra.skillCount` 按ID推定，标清证据来源；无法可靠确认右值时须标记待核验，不把推定写成实测事实。
4. 形成候选阵容后，先按优先级锁定前三主力，再分配其余队伍，必须用 `工具/配将服务/validate_lineup.py` 做全局检查，并用 `audit_consultation.py` 检查正式报告字段。`errors` 未清零不得交付；`warnings` 必须逐条人工判断；`notes` 中的暂定赛季来源只有在会改变方案时才请用户核验。
5. 完整账号咨询在配将验收后再做施政两案。输出应逐队交代站位与全部战法、核心逻辑、速度、优势与主要克制、替代成本、觉醒/拆解代价、跨队资源冲突；未上队的重要五星说明原因。
6. 使用5–10份覆盖常见对手的代表战报反馈，记录实际行动顺序、首个控制/增益、主伤害源、前三回合爆头和重复问题；不得凭单场胜负调整队伍。可用 `analyze_battle_reports.py` 做汇总。
7. 自动检查只负责可结构化的硬规则与风险提示；阵容强度、拆解价值、宝物、加点、复杂联动和施政收益仍需当前文本与战报判断，禁止把脚本通过写成强度保证。赛季门禁由 `season_gate.py` 区分“已有可继续用”和“当前能新获取”，XP暂定项只在实际改变方案时核验。

## 精编报告强制闭环（2026-09-09 用户固化）

### 适用范围

- 重制任何旧精编或精修报告。
- 从新视频、静帧、音频或转写首次制作精编报告。
- 对已有报告做批量优化、修正或标杆迁移。

### 必须依次完成的四个阶段

1. **制作或重制**
   - 按 `资料库/当前精编报告标杆.md` 组织正文。
   - 只保留可迁移的事实、条件、机制判断、建议或风险；不照搬作者阵容，不用单场战报代表普遍强度。
   - 需要溯源时，先使用视频、静帧、音频或转写完成证据锁定；闭环完成前不得删除上游材料。

2. **结合本地资料库审查**
   - 制作者必须再以“AI 学习者”视角完整阅读成品，不得以“已渲染”代替审查。
   - 用当前机制库、武将库、战法库、版本解析规则、战法冲突规则与误识别映射表交叉检查。
   - 至少审查：事实准确性、武将版本、战法机制与冲突、论证是否越界、案例是否被误当通用答案、信息是否足以脱离源文件独立学习。
   - 给出学习价值结论：`高`、`普通`或`不建议保留`，并说明可学内容和不可直接迁移内容。

3. **修改与再审**
   - 有确切证据的错误由制作者直接修正，并同步修改会在下次渲染中覆盖成品的母本或生成器。
   - 修改后重新执行第 2 阶段，直到内容、边界与学习价值判断自洽。
   - 只有真正需要人眼读图、多个合理版本无法排除，或证据相互冲突时，才暂停并请用户核验；在用户给出结果前不得继续该项。
   - 若报告没有足够的可迁移知识，优先降级或放弃，不为凑数保留。

4. **验收与汇报**
   - 执行正文与表格文字检查、残留词检查、样式/页面结构检查和逐页渲染检查。
   - 正式覆盖后校验候选文件与正式文件一致，并同步 `reports_index_rows.json` 与 `reports_index.md`。
   - 向用户汇报：本批数量、每份的学习等级、主要修正、适合学习的内容、不可直接迁移的边界、未解决疑问与成品路径。

### 完成判定

- 四个阶段必须按顺序闭环：**重制/制作 → 资料库审查 → 必要修改与再审 → 验收汇报**。
- 任一阶段未完成，该报告不得标记为“制作完成”、不得进入正式保留库，也不得建议删除对应溯源材料。
- 审查后无需修改时，仍必须记录“已审查，无需修改”，不得跳过第 3 阶段的结论留痕。
