## ⚠️ 字段语义坑（星级曾三次大面积出错）

1. **hero_extra.quality 的数字不是实际星级**。2026-09-20 按同一武将ID且 `hero_extra.methodId=hero.json.skill_init` 全库复核 393 条：`2-UC→3星` 68条、`3-R→4星` 156条、`4-SR→5星` 169条，均与 `hero.json.quality` 一致。旧文“`4-SR=4星、hero_extra无5星卡`”已证伪，禁止沿用；账号解析直接读取精确ID的 `hero.json.quality`，匹配失败留待核验。
2. **hero.json 同名多条**（普通/SP/XP/界限版）——按首条/末条取都会错；quality 有 6（=UR界限版，非 5 星）。
3. **首选版本锚点 = methodId 精确匹配**：`hero_extra.methodId → hero.json.skill_init → quality`（自带战法 ID 锁定版本）。若画面没有自带战法，可用同帧“武将名+阵营+总星数+SP/XP/无标识”唯一反查；不得只按姓名、星级或库顺序。
4. 子智能体 desc 的"X星"不可靠（曾把红度 4 误读为 4 星）。用户肉眼核验是重要证据，但用户也可能记错或看错；若用户结论与当前官方数据、可读卡面或唯一 ID 链冲突，必须先复核并展示证据，不得机械覆盖资料库。

## 星级权威固化表

- `资料库/hero_star_fixed.json`：298 武将星级固化（3星65/4星92/5星140/6星1），生成器 `_star_of()` 优先级：**固化表 → methodId 匹配 → hero.json 首条**。⚠️ **此表用众数法生成，对同名双版本武将（如朱儁/甘宁/凌统既有 4 星版又有 5 星版）会记成较常见的版本星级，给出错误值**——故固化表仅作「无自带战法时的回退」，生成器渲染器 (`hero_label_by_skill`) 现已改成「自带战法 → method_map[战法].star 优先，_star_of 仅回退」，不得将固化表值覆盖战法精确值。
- 维护：新增武将先 methodId 匹配核验，用户确认后追加固化表。

## 来源优先级

官方接口 JSON ＞ 网易大神 ds.163.com ＞ 官网图鉴页文案。

## 战法标签与获取阶段（2026-09-14）

- `资料库/official_skill_db.json` 的每条规范战法记录包含原始 `season_code` 与规范 `season_tag`。字段由 `aa_rate_supplement.json` 按规范战法 ID 精确关联，禁止只按战法名合并。
- 标签映射：`0 → BASE`、`2 → S2`、`3 → S3`、`4/40003 → XP`。**XP只是战法标签，不是赛季；严禁把XP直接解释成征服赛季。**
- 获取阶段只读取单条战法的 `acquisition_stage`。当前已确认：S2/S3标签按对应赛季；征服赛季市井战法按获取说明；形兵之极、磐阵善守为S3。没有该字段的XP战法仍属待核定。
- `obtain_method` 只区分市井购买、拆解指定武将、兑换三类，不凭获取方式直接推断开放赛季。
- XP标签且通过拆解指定武将获得的战法：来源武将尚未逐张核实时，按用户决定暂记为征服赛季，`acquisition_stage_status=provisional_default`；这是一条保守门禁，不是已证实事实。后续某个战法对配将价值较高时，再请用户核查其全部有效拆解武将卡包，并改为`confirmed`或更正赛季。
- XP标签且通过兑换获得、但本地没有明确开放赛季的战法，同样按用户决定暂记为征服赛季并标注`provisional_default`。当前共15个；只有某项会实际影响配将结论时，才请用户核查该战法的开放赛季。
- 2026-09-14清晰卡包截图已确认：XP左慈、XP辛宪英、XP吾粲、XP于禁均可从征服赛季卡包获取。衡轭的三个有效拆解来源（辛宪英、吾粲、于禁）已全部覆盖，因此衡轭确认为征服赛季获取；令无空悬仍有XP黄忠来源未核实，暂按默认规则处理。
- 配将时，明确晚于当前赛季的战法必须排除；拆解类和兑换类的暂定征服赛季战法也先排除，但若它会显著改变方案，应提示用户进一步核验，不能把暂定结论写成已证实事实。
- 标签与获取阶段均不证明账号已经拥有或一定能完成拆解/兑换，账号事实仍以当次截图为准。
- 战法显示 `左/右`：用户 2026-09-20 明确左边=当前空闲份数、右边=账号可分配总份数、差值=已分配份数。`0/1` 不是未拥有；`0/3` 表示3份已分配；`1/2` 表示仍有1份可直接分配。百家社原始导出 `[战法ID, 数字]` 当前只给左值；右值暂按ID从本地 `skill_extra.skillCount` 补出，必须标明是资料库推定而非账号导出实测。全量重组时旧队可收回份数=右−左；仅明确保留的旧队占用应继续扣除，禁止只按左值限制重配。
- `skill_extra.notice` 若写有“可配置N个武将”，应与 `skillCount` 交叉核对；一致仅能佐证资料库自身的总份数，不能证明当前账号页面右值。相同ID的重复行只有内容完全一致才可折叠；若同ID内容冲突或 `notice` 与 `skillCount` 冲突，停止推定该战法总份数并核验。

## 官方机制参考库（2026-08-28 用户指定）

- 入口：`https://stzb.163.com/m/strategy/`
- 定位：**可参考机制库**。用于理解官方基础玩法与系统逻辑，例如战法、战斗、部队配置、武将、设施、地图、势力、同盟、国家科技。
- 使用边界：该目录可见文章多为早期内容；可引用其机制框架和名词解释，但**不得**直接据此确认当前赛季数值、武将/战法参数、强度、适用阵容或政策效果。
- 版本敏感事项仍须以当前客户端面板、当前官方接口/公告或用户提供的游戏内截图复核；无法复核时明确标注“不足以确认”。

## 星级判定铁律补充（2026-08-22 用户批评后固化）
- **星级判断首选资料库 methodId**（hero_extra.methodId → hero.json.skill_init → quality），**包括 4 星版本**：如 甘宁（轻侠妄为 200624=4星 vs 侵掠如火 200034=5星）、朱儁（节镇关东 200040=4星 vs 西乡武功 200791=5星）、凌统（国士 200629=4星）。无自带战法时，允许以可回查的完整卡面证据唯一锁定；不能唯一则不输出具体版本。
- **禁止把资料库能确认的星级无理由交给用户重复核验**——用户主要复核资料库冲突/覆盖不到的场景；用户结论与可复核证据冲突时，以重新核查后的证据链为准，并明确说明分歧。
- 报告/JSON 的星级标注（渲染器 methodId 匹配结果）即为最终答案，不自疑、不问用户。

## 星级判定特例：陈寿·敏学 升星（2026-08-22 用户核验确立）
- **敏学特性**：陈寿武将的「敏学」= 提升武将星级至五星 + 随机大幅提升属性 + 有概率进阶高级兵种。
- **敏学只升星不换自带战法**：4 星卡（甘宁·轻侠妄为）敏学后画面 5 星极、战法仍轻侠妄为——此时 methodId 匹配=原始 4 星 ≠ 画面 5 星，**属正常特例，以画面为准**，禁止按 methodId 把画面 5 星判成 4 星、也禁止把自带战法改写成侵掠如火。
- **落地机制**：JSON entities.heroes 加 `star_override`（值=画面星级）+ `star_override_reason`；渲染器 `_apply_star_override()` 优先用 override。参考：率土之滨队伍推荐第16队（宁元刀）甘宁。
- **通用教训**：画面星级与 methodId 冲突时先找画面证据（战法面板/特性字幕），不要急于改战法或改星级。

## 星级判定补充 2：同名多版本取众数（2026-08-22 全量核验修复）
- **禁止"同名多版本取最高/取首条"**：hero.json 同一 skill_init 可能含 界限版(UR 6星)+普通/S2/SP(5星)——吕布辕门射戟 200012=6星(界限)×1 + 5星×3，取最高=6（错）、取首条=6（错），**取众数=5（对）**。
- **排除 quality=1 野怪**：hero.json 含山贼/流寇/强盗（quality=1，共用战法码如 200103 强攻）——众数前先排除，否则宋谦/丁原被标 1 星。
- skill_init=200100 是**界限版通用码**（李肃/魏续等），不是具体武将自带战法 ID，不可用于精确匹配。
- 渲染器实现：si_star 众数化 + _hero_star_best 直接查固化表（不再 max）。
